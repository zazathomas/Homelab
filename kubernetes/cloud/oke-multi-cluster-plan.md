# OKE multi-cluster platform plan

## Decision

Keep the two OKE clusters as independent Kubernetes clusters. Do not merge their control planes.

Use:

- Karmada on the existing homelab cluster as the multi-cluster control plane.
- Pull-mode registration for the two OKE member clusters unless private API connectivity and OCI authentication are already solved for Push mode.
- Argo CD as the GitOps source of truth, targeting Karmada for workloads that are approved to span both OKE clusters.
- Cluster-local management for Cilium, ingress, storage, CSI drivers, operators, secrets, and monitoring agents.
- Cloudflare with separate origins and health checks for public traffic failover.

The result is one workload management platform. It is not one Kubernetes cluster. Each OKE cluster keeps its own API server, scheduler, nodes, networking, storage, and platform components.

Karmada does not provide cross-cluster pod networking, storage replication, or live pod migration.

## Target topology

```text
Argo CD on the homelab cluster
              |
       Karmada API/control plane
              |
       +------+------+
       |             |
    OKE member A   OKE member B
```

The Karmada host cluster must remain available to manage both members. If the homelab is not a suitable control-plane host, use a dedicated OCI VM or a third Kubernetes cluster instead.

## Registration mode and connectivity

### Preferred mode: Pull

Use Pull mode when the homelab cannot reliably reach the OKE API endpoints. A `karmada-agent` runs for each OKE member and connects to the Karmada API.

Pull mode requires:

- A stable TLS endpoint for the Karmada API that both OKE clusters can reach.
- Private routing through WireGuard, site-to-site VPN, VCN connectivity, or another protected network path.
- Firewall rules allowing the OKE clusters to reach the Karmada API.
- A bootstrap token and agent registration for each member.

The Karmada API should not be exposed broadly to the public internet. If a public endpoint is unavoidable, restrict its source ranges and use the Karmada authentication and TLS configuration from the official registration guide.

Representative registration flow:

```bash
# On the Karmada control plane
karmadactl token create \
  --print-register-command \
  --kubeconfig "$KARMADA_KUBECONFIG"

# Run the generated command for each OKE member.
# Supply the member kubeconfig and a stable cluster name.
karmadactl register <karmada-api-endpoint> \
  --cluster-name oke-a \
  --kubeconfig "$OKE_A_KUBECONFIG"

karmadactl register <karmada-api-endpoint> \
  --cluster-name oke-b \
  --kubeconfig "$OKE_B_KUBECONFIG"
```

Use the exact command generated by the installed Karmada version. Verify the resulting mode and status:

```bash
kubectl --kubeconfig "$KARMADA_KUBECONFIG" get clusters
```

### Push mode

Use Push mode when the Karmada control plane can reach both OKE API servers directly:

```bash
karmadactl join oke-a \
  --kubeconfig "$KARMADA_KUBECONFIG" \
  --cluster-kubeconfig "$OKE_A_KUBECONFIG"

karmadactl join oke-b \
  --kubeconfig "$KARMADA_KUBECONFIG" \
  --cluster-kubeconfig "$OKE_B_KUBECONFIG"
```

Push mode needs more than a successful `karmadactl join`. Current OKE kubeconfigs use an `exec` plugin that runs `oci ce cluster generate-token`. The Karmada controller must be able to execute that command and access OCI credentials at runtime. Installing the OCI CLI only on the machine that runs `karmadactl join` is not enough.

Use Push mode only after verifying that the Karmada controller can authenticate continuously to both OKE APIs. Pull mode is the simpler default for a Karmada control plane running in the homelab.

## OKE access and network preparation

Generate a separate kubeconfig for each OKE cluster:

```bash
oci ce cluster create-kubeconfig \
  --cluster-id "$OKE_A_OCID" \
  --file "$HOME/.kube/oke-a.config" \
  --region "$OKE_A_REGION" \
  --token-version 2.0.0 \
  --kube-endpoint PRIVATE_ENDPOINT
```

Use `PUBLIC_ENDPOINT` only when the endpoint is intentionally public and restricted to trusted source addresses.

Collect the following from both OKE clusters before installing Karmada or changing networking:

- Kubernetes version and OKE cluster type.
- CNI plugin and kube-proxy configuration.
- Pod, service, node, VCN, and subnet CIDRs.
- API endpoint type, DNS name, and reachable addresses.
- VCN, subnet, route table, NSG, and security-list configuration.
- Allocatable and requested CPU and memory.
- Existing ingress, storage, operators, and network policies.

For private OKE API endpoints, establish private routing before registration. For public endpoints, restrict TCP 6443 to the Karmada egress address. Keep the standard OKE worker, API endpoint, pod, and node security rules intact.

## Karmada installation

Install the Karmada CLI on the administration host, then initialize Karmada on the selected host cluster:

```bash
kubectl karmada init --kubeconfig "$HOST_KUBECONFIG"
```

The default installation places Karmada components in `karmada-system` and creates a Karmada API kubeconfig. Record that kubeconfig in a protected location. Do not commit it to this repository.

Verify the control plane before registering members:

```bash
kubectl --kubeconfig "$HOST_KUBECONFIG" \
  -n karmada-system get pods

kubectl --kubeconfig "$KARMADA_KUBECONFIG" get --raw=/version
kubectl --kubeconfig "$KARMADA_KUBECONFIG" get clusters
```

For production use, configure Karmada API server and etcd replicas according to the host cluster's capacity. A single Karmada control plane is acceptable for the pilot, but it is a management-plane single point of failure.

## Cluster metadata

Give the members stable names and labels that policies can use:

```bash
kubectl --kubeconfig "$KARMADA_KUBECONFIG" label cluster oke-a \
  platform.example.com/provider=oci \
  platform.example.com/region=<region-a> \
  --overwrite

kubectl --kubeconfig "$KARMADA_KUBECONFIG" label cluster oke-b \
  platform.example.com/provider=oci \
  platform.example.com/region=<region-b> \
  --overwrite
```

Record the actual region, zone, capacity, and workload restrictions in the cluster inventory. Do not use labels as a substitute for verifying actual available capacity.

## Placement model

Only workloads with an explicit propagation policy may span clusters. The default should remain cluster-local.

For stateless Deployments:

- Use `Divided` replica scheduling when the total replica count should be shared between clusters.
- Use `Duplicated` scheduling when each cluster should receive the full replica count.
- Use `spreadConstraints` when both clusters must be selected.
- Use dynamic available-replica weighting only after resource requests and capacity reporting are correct.
- Use explicit cluster affinity for workloads that must stay in one region or cluster.

Example policy for a four-replica stateless workload:

```yaml
apiVersion: policy.karmada.io/v1alpha1
kind: PropagationPolicy
metadata:
  name: web
  namespace: web
spec:
  resourceSelectors:
    - apiVersion: apps/v1
      kind: Deployment
      name: web
  placement:
    clusterAffinity:
      clusterNames:
        - oke-a
        - oke-b
    spreadConstraints:
      - spreadByField: cluster
        minGroups: 2
        maxGroups: 2
    replicaScheduling:
      replicaSchedulingType: Divided
      replicaDivisionPreference: Weighted
      weightPreference:
        dynamicWeight: AvailableReplicas
```

Apply the workload and policy to the Karmada API, not directly to either member:

```bash
kubectl --kubeconfig "$KARMADA_KUBECONFIG" apply -f deployment.yaml
kubectl --kubeconfig "$KARMADA_KUBECONFIG" apply -f propagation-policy.yaml

karmadactl get deployment --operation-scope all
```

Karmada places new replicas. It does not live-migrate running pods or their data.

## Service discovery and ingress

A normal Kubernetes Service is local to one member cluster. Karmada propagation alone does not make it globally routable.

For the initial design:

- Run ingress independently in both OKE clusters.
- Give each ingress an independent OCI load balancer or other reachable endpoint.
- Use Cloudflare health checks and origin failover for public traffic.
- Keep application Services cluster-local.

For applications that require cross-cluster service discovery, add Kubernetes MCS resources. MCS requires connected member-cluster networks and non-overlapping pod and service CIDRs. Validate the network path before propagating `ServiceExport` and `ServiceImport` resources.

Cilium Cluster Mesh is optional. It is not required for Karmada scheduling. Treat it as a separate networking project and add it only after the Karmada workload pilot succeeds.

## CNI and cross-cluster networking

The repository currently contains a custom Cilium configuration with `10.244.0.0/16` as a cluster pool. Do not assume the same CIDR can be reused on both OKE clusters. Pod, service, node, VCN, and load-balancer ranges must be checked for overlap.

Before attempting Cilium Cluster Mesh:

- Confirm both clusters use a supported OKE networking model.
- Confirm unique Cilium cluster names and numeric IDs.
- Confirm non-overlapping pod and service CIDRs.
- Confirm private routing between the required node and pod addresses.
- Confirm MTU, DNS, NSG, and security-list behavior.
- Confirm compatible Kubernetes and Cilium versions.
- Test on a noncritical cluster first.

Do not remove Flannel or kube-proxy from an OKE cluster as part of the Karmada installation. Any CNI migration must be planned and tested separately.

## Karmada and GitOps

Register the Karmada API as an Argo CD destination. Argo CD should apply the workload manifests and Karmada policies to Karmada. Karmada should then propagate approved resources to the OKE members.

The current repository ApplicationSets target the local Kubernetes API with `https://kubernetes.default.svc`. Add a separate ApplicationSet or Argo CD Application targeting the Karmada API. Keep cluster-local applications under their existing per-cluster paths.

The ownership split should be:

- Argo CD to Karmada: application manifests and Karmada policies for multi-cluster workloads.
- Argo CD directly to each OKE cluster: Cilium, ingress, storage, CSI drivers, External Secrets, OCI Vault integration, operators, and monitoring agents.
- Karmada to OKE clusters: only resources selected by propagation policies.

Do not have Argo CD and Karmada independently reconcile the same member-cluster resources.

## Stateful workloads

Keep stateful workloads and their PVCs pinned to a designated OKE cluster during the initial rollout.

Do not propagate StatefulSets, PVCs, or local-storage resources between clusters until the application has a tested replication and recovery design.

Use external backups or application-level replication for recovery. The existing CloudNativePG object-storage backup path should remain separate from Karmada placement. Secrets should stay cluster-local and continue to come from External Secrets and OCI Vault.

## Failure handling

For stateless workloads:

1. Detect member-cluster loss.
2. Confirm the cluster becomes unavailable in Karmada.
3. Apply the documented Karmada failover and taint behavior.
4. Reschedule eligible replicas to the healthy member when capacity allows.
5. Remove failed-cluster endpoints from public routing.
6. Confirm Cloudflare converges on the healthy origin.

Karmada automatically uses unhealthy-cluster taints for scheduling decisions, but failover behavior still depends on the policy, scheduling type, capacity, and configured tolerations. Test the exact behavior with the installed Karmada version.

For stateful workloads, keep promotion and restoration manual. Select the source of truth, fence the failed service, restore or promote the data service, update placement, and verify consistency before reopening traffic.

## Implementation phases

### 1. Inventory

Collect the OKE versions, CNI settings, CIDRs, API endpoint details, routing, security rules, capacity, ingress, storage, and operators.

### 2. Choose the management path

Prefer Pull mode with a private VPN path from both OKE clusters to the homelab Karmada API. Use Push mode only when direct API access and OCI exec authentication from the Karmada controller have been verified.

### 3. Install Karmada

Install Karmada on the homelab host cluster. Verify the control plane before registering any member.

### 4. Register both OKE members

Register `oke-a` and `oke-b`. Verify that both clusters report the expected Kubernetes version, mode, health, and capacity.

### 5. Run the Karmada workload pilot

Use a noncritical stateless HTTP service with:

- CPU and memory requests.
- An explicit propagation policy.
- Replica distribution across both OKE clusters.
- Cluster-local Services and ingress.
- Cluster-local secrets.
- Independent Cloudflare origins.

Test capacity changes, member-cluster failure, replica rescheduling, endpoint removal, traffic failover, and recovery.

### 6. Integrate Argo CD

Register Karmada as an Argo CD destination. Move the pilot workload and policy into Git. Keep member-cluster platform resources under direct per-cluster reconciliation.

### 7. Add cross-cluster networking only if required

After the pilot is stable, evaluate MCS and Cilium Cluster Mesh for applications that need cross-cluster service access. Resolve all CIDR and routing conflicts first.

### 8. Expand gradually

Move additional stateless services after the pilot passes. Keep databases, PVC-backed services, operators, and other stateful systems cluster-local until each has a separate recovery design.

## Pilot exit criteria

The pilot is complete when all of these are demonstrated:

- Both OKE clusters register successfully with Karmada.
- Karmada places replicas according to the propagation policy.
- The workload runs in either OKE cluster without manifest changes.
- Cluster-local ingress works independently in both members.
- Cloudflare fails over between the two origins.
- Stateless replicas are rescheduled after a member-cluster failure.
- Failed-cluster endpoints stop receiving public traffic.
- Cluster-local secrets remain managed by External Secrets.
- Karmada, ingress, capacity, and failover health are visible in monitoring.
- Stateful recovery remains documented as a manual process.
